What an application exposes to a MCP client, and how. Everything here lives in
`io.yupiik.fusion.mcp.api`: two build time markers plus two runtime SPIs.

[options="header",cols="1,2,2"]
|===
| Page | Exposes | Through
| xref:tools.adoc[Tools] | what the model can call | `@MCPTool` on a `@JsonRpc` method
| xref:prompts.adoc[Prompts] | templates the user picks, and their argument completion | `@MCPPrompt` and `MCPCompletions`
| xref:resources.adoc[Resources] | data the client can read and attach | the `MCPResources` bean
| xref:server-to-client.adoc[Server to client] | logging, notifications, sampling, elicitation, roots | `MCPNotifier` and `MCPSession`
|===

== Choosing the right one

[options="header",cols="1,3"]
|===
| Need | Use
| The model should be able to *act* or *look something up* | a xref:tools.adoc[tool]
| The *user* should be able to trigger a prepared instruction | a xref:prompts.adoc[prompt]
| The client should be able to *read data* and attach it to the conversation | a xref:resources.adoc[resource]
| The server needs to *tell* the client something happened | a xref:server-to-client.adoc[notification]
| The server needs the client model, its user or its workspace | a xref:server-to-client.adoc[server to client request]
|===

TIP: tools and prompts are code, known at build time, hence the annotations; resources are data, discovered at
runtime, hence the SPI. See xref:../internals/design.adoc[Design] for the reasoning.

== Common ground

* every extension point is a plain Fusion bean or method: constructor injection, scopes and `@Order` all work as
usual,
* nothing is reflective: the descriptors and the JSON codecs are generated at build time,
* a method can be asynchronous (`CompletionStage<T>`) and can take a
`io.yupiik.fusion.http.server.api.Request` parameter to reach the MCP session,
* what a client is told the server can do - its capabilities - is computed from what is actually deployed, so an
empty extension point is never advertised.
